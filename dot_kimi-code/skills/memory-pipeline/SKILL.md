# Memory Pipeline

This is the reference for how the development pipeline uses ai-memory: the namespace conventions and the query/write pattern per phase. Every agent's own "Memory integration" section is the compact, agent-specific instantiation of the tables below; keep new agents consistent with this reference instead of loading it every session.

## Namespaces

- `decisions/<slug>.md` — architectural, product, or scope decisions. Use ADR structure.
- `gotchas/<subsystem>.md` — reproducible traps in a subsystem. Include repro and workaround.
- `procedures/<task>.md` — repeatable steps. Include verification.
- `rules/<topic>.md` — project rules. Keep short and pinned.
- `sessions/` — auto-generated by ai-memory. Do not write manually.
- `_global/rules/` — your personal rules. Do not write project rules here.

## Query patterns by phase

Before starting work in any phase, run `memory_query` with the pattern below. If the result is thin, broaden the query or check sibling projects.

| Phase | Query pattern |
|---|---|
| product-discovery | "product decisions", "user constraints", "market research", "anti-goals" |
| brainstorming | "design options", "rejected alternatives", "principles", "constraints" |
| grill-me | "previous gaps", "questioned decisions", "open questions" |
| srs | "existing requirements", "domain conventions", "scope decisions" |
| architecture-design | "ADRs", "integration patterns", "data model decisions", "business rules" |
| implementation-plan | "tracker items", "slicing patterns", "blockers", "implementation surface" |
| implementation | "subsystem gotchas", "implementation decisions", "failed approaches" |
| pull-request | "review findings", "security constraints", "spec requirements" |

## What to write after each phase

Write a durable page only when the phase produced knowledge that survives the session. Do not write routine progress.

| Phase | Write when | Namespace |
|---|---|---|
| product-discovery | new product decision, new constraint, new anti-goal | `decisions/` |
| brainstorming | design approved, options rejected | `decisions/` |
| grill-me | gap confirmed, question answered | `decisions/` or `gotchas/` |
| srs | new requirement, new convention | `decisions/` or `rules/` |
| architecture-design | new ADR, new integration pattern, new business rule | `decisions/` |
| implementation-plan | new slicing pattern, new tracker convention | `procedures/` or `rules/` |
| implementation | new gotcha, new procedure, failed approach to avoid | `gotchas/` or `procedures/` |
| pull-request | new review finding, new security rule | `gotchas/` or `rules/` |

## Handoff between phases

When a phase ends and another begins, the next agent receives:

- A short handoff with what was decided, open questions, and next steps.
- Links to durable pages created in the previous phase.

Use `memory_handoff_begin` only at session end or when the user explicitly asks. Do not use handoffs for routine phase transitions within the same session.

## Auto-improve

After a session rich in decisions or gotchas, run `memory_auto_improve` to propose durable pages. With `require_approval = true`, review proposals before applying. Accept only what generalizes.

## Global rules

Default memory reads surface `_global/rules/` pages in every project. Do not repeat them in skills or agents. Consult `_global/rules/` when you need the full text.

## Feedback

When a retrieved page is stale or wrong, call `memory_feedback` with the page path and signal. This improves future retrieval.
